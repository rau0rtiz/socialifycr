# Project Rules
- Client calendar installability is manifest-only, with a public metadata-only calendar-manifest endpoint providing token-specific IDs/start URLs and calendar-only Apple head tags; do not register an app-shell service worker. Why: installed shortcuts must reopen the correct client calendar without caching stale previews or affecting agency branding.
- Static calendar artwork uses the shared CalendarThumb with intrinsic proportions in full-width cards and review dialogs; fixed-size backlog thumbnails contain rather than crop it. Why: agency and public readers must see the same complete photo or post without video-shaped framing.
- Shared calendars own their viewport scroll container and public piece dialogs use one native scroll container with a two-column media/review layout. Why: isolate public scrolling from PWA body locks and keep review controls beside the media instead of below a stretched grid row.
- CalendarMonth enables its compact mobile month grid through an explicit public-view prop; agency mobile layouts keep their existing agenda. Why: isolate public presentation changes from internal scheduling workflows.

- Dialogs and overlays mounted through a React portal (outside `.agency-shell` / `.noeval-scope`) must not rely on scoped theme classes; give them their own token block in `index.css` (see `.socialify-clapper`). Why: portal output escapes the scope selector, so those color utilities silently stop applying.
- Documentation-to-production import asks AI only for source-line ranges and classifications; server code copies original text, never AI-authored prose. Why: avoids rewriting and minimizes output tokens while keeping unlabelled source details.
- Publication calendar items (`content_calendar_items`) are upserted by `shot_id` from `clickup-create-tasks`; the client-facing `/calendario/:token` reads and writes only through the `calendar-public` edge function. Why: tables stay agency-only under RLS while the shared link needs no login.
- Calendar videos are stored as links (Drive/Milanote), never uploaded. Why: the agency already pays for that storage and video files are too heavy for the app.
- Calendar media players keep every control and the Socialify label strip under the media, never above it; Drive links play through a native video element and fall back to Drive's own embed only when the file cannot be streamed directly. Why: Drive's embed puts its toolbar on top of the picture, and playback controls must sit below the video for agency and client readers alike.
- Both calendar views render the same comment-history component from persisted comments, independent of item status. Why: author attribution and Costa Rica timestamps must remain consistent for agency and shared-link readers.
- Calendar-origin pieces use calendar-clickup for creation and server-validated client-space/list mapping; creation claims are service-role-only and uncertain external outcomes stay locked for review. Why: avoid cross-client task destinations and duplicate tasks after network failures without changing production-sheet export semantics.
- Calendar ClickUp configuration stores a client space, not a default list; sync discovers all foldered and folderless lists on every run, while creation chooses and validates a destination list inside that space. Why: each production has its own list and a client's monthly deliveries can span multiple productions.
- Calendar monthly scheduling targets live in agency-only `content_calendar_goals`, uniquely keyed by client and month; pace compares dates scheduled up to today with proportional elapsed-month coverage, not actual publication. Why: keep delivery planning separate from legacy platform analytics goals and avoid claiming pieces were published.
- ClickUp→calendar sync lives in `clickup-create-tasks` as action `sync_calendar` (agency JWT or `x-sync-secret` header; hourly cron). It explicitly discovers lists per folder and folderless lists, reads all task pages including subtasks and tasks in multiple lists, and imports untagged tasks as `otro`; only production ops and shared-rule excluded statuses are skipped. Imports start unscheduled and never write delivery dates. Why: task labels and closed-status types must not prevent client-space imports, and editing deadlines remain independent from delivery dates.
- Calendar approval moves the ClickUp task to "aprobado" only when the piece is fully approved: video-type pieces (reel/tiktok/short) with a cover need video + cover approved, otherwise only the piece; partial approvals leave a comment only. Status matching prefers exact names over partial ones (e.g. "aprobado" beats "pre-aprobación"). Why: the task must not read as client-approved while the cover is still pending.
- ClickUp sync uses the legacy `clickup_approved` flag as calendar exclusion metadata, separate from review status; both calendars and overview filter flagged pieces, while saved dates and history remain untouched. Clients without spaces refresh only already-linked tasks with paced reads. Why: honor external workflow exclusions consistently without deleting historical records or changing client review approvals.

# Project Rules
- Use campaignAds for scoped ad lists. Why: keep each campaign's ranking isolated in summaries and dialogs.
- Client calendar installability is manifest-only, with a public metadata-only calendar-manifest endpoint providing token-specific IDs/start URLs and calendar-only Apple head tags; do not register an app-shell service worker. Why: installed shortcuts must reopen the correct client calendar without caching stale previews or affecting agency branding.
- Static calendar artwork uses the shared CalendarThumb with intrinsic proportions in full-width cards and review dialogs; fixed-size backlog thumbnails contain rather than crop it. Why: agency and public readers must see the same complete photo or post without video-shaped framing.
- Shared calendars own their viewport scroll container and public piece dialogs use one native scroll container with a two-column media/review layout. Why: isolate public scrolling from PWA body locks and keep review controls beside the media instead of below a stretched grid row.
- CalendarMonth enables its compact mobile month grid through an explicit public-view prop; agency mobile layouts keep their existing agenda. Why: isolate public presentation changes from internal scheduling workflows.

- Dialogs and overlays mounted through a React portal (outside `.agency-shell` / `.noeval-scope`) must not rely on scoped theme classes; give them their own token block in `index.css` (see `.socialify-clapper`). Why: portal output escapes the scope selector, so those color utilities silently stop applying.
- Documentation-to-production import asks AI only for source-line ranges and classifications; server code copies original text, never AI-authored prose. Why: avoids rewriting and minimizes output tokens while keeping unlabelled source details.
- Publication calendar items (`content_calendar_items`) are upserted by `shot_id` from `clickup-create-tasks`; the client-facing `/calendario/:token` reads and writes only through the `calendar-public` edge function. Why: tables stay agency-only under RLS while the shared link needs no login.
- Calendar videos are stored as links (Drive/Milanote), never uploaded. Why: the agency already pays for that storage and video files are too heavy for the app.
- Calendar media players keep every control and the Socialify label strip under the media, never above it; Drive links play through a native video element and fall back to Drive's own embed only when the file cannot be streamed directly. Why: Drive's embed puts its toolbar on top of the picture, and playback controls must sit below the video for agency and client readers alike.
- Both calendar views render the same comment-history component from persisted comments, independent of item status. Why: author attribution and Costa Rica timestamps must remain consistent for agency and shared-link readers.
- Calendar-origin pieces use calendar-clickup for creation and server-validated client-space/list mapping; creation claims are service-role-only and uncertain external outcomes stay locked for review. Why: avoid cross-client task destinations and duplicate tasks after network failures without changing production-sheet export semantics.
- Calendar ClickUp configuration stores a client space, not a default list; sync discovers all foldered and folderless lists on every run, while creation chooses and validates a destination list inside that space. Why: each production has its own list and a client's monthly deliveries can span multiple productions.
- Calendar monthly scheduling targets live in agency-only `client_delivery_targets`, uniquely keyed by client and content type; pace compares dates scheduled up to today with proportional elapsed-month coverage, not actual publication. Why: keep delivery planning separate from legacy platform analytics goals and avoid claiming pieces were published.
- ClickUp→calendar sync lives in `clickup-create-tasks` as action `sync_calendar` (agency JWT or `x-sync-secret` header; hourly cron). It discovers foldered and folderless lists, all task pages, subtasks and multiple-list tasks; untagged tasks import as `otro`, only production ops are hidden. Final tasks are approved; verified historical dates apply only to the once-per-client import atomically claimed via `clients.calendar_history_imported_at` before writes (interrupted imports fail closed). Existing calendars are migrated as already imported. Ordinary sync never assigns or restores dates; initial writes are null-only and never use editing deadlines or date_updated. Why: preserve the PM's scheduling and prevent concurrent/retried sync from undoing it.
- Calendar approval moves the ClickUp task to "aprobado" only when the piece is fully approved: video-type pieces (reel/tiktok/short) with a cover need video + cover approved, otherwise only the piece; partial approvals leave a comment only. Status matching prefers exact names over partial ones (e.g. "aprobado" beats "pre-aprobación"). Why: the task must not read as client-approved while the cover is still pending.
- ClickUp sync clears the legacy exclusion flag for content tasks, including final statuses; the flag hides only production ops. Final statuses mark piece review approved and remain visible in both calendars; a calendar approval without a final ClickUp status is reverted to pending on sync, except a client video approval awaiting its cover. Clients without spaces refresh only linked tasks with the same approval/date rules. Why: approved and uploaded content must remain in the client publication calendar.
- Calendar sync deletes a linked calendar item only after a direct task lookup confirms ClickUp's task-not-found/deleted response; configured spaces reconcile missing tasks after all list pages succeed, and legacy clients use the same check. Why: remove externally deleted pieces without interpreting archived/moved tasks or permissions and network failures as deletions.
- Public calendar cards and day cells show the agency-uploaded `thumbnail_url` with a type label (typographic placeholder when absent); production-sheet exports never copy the sheet photo into calendar items. Why: clients must identify which piece is which without misleading inherited images.

- Calendar pieces mirror the exact ClickUp status name/color (`clickup_status`, `clickup_status_color`) set by sync, client review and the agency status picker (`calendar-clickup` set_status writes ClickUp first); the internal `status` stays for approval logic. Why: both calendars must read the same label as ClickUp, whichever side changed it.
- Carousel pieces store ordered slide URLs in `content_calendar_items.carousel_urls`; the first slide is mirrored into `thumbnail_url` for cards, and both calendars render slides through the shared VideoPlayer/CarouselViewer. Why: clients review every slide in the agency's intended order.
- The client results dashboard lives behind the calendar share link (`/calendario/:token`, tabs) and reads only through the `client-dashboard` edge function, which uses the agency Meta connection server-side, groups results by per-campaign result type (objective or agency override, never summed across types) and caches per client+range for an hour with stale fallback; setup lives in its own agency menu section. Why: clients need no login or Meta access, and mixed campaign goals must stay comparable.
- Client dashboards select a Meta business portfolio before advertising accounts; client-dashboard validates owned/shared portfolio membership on save, campaign reads and public results, with portfolio/account-scoped cache keys. Why: global agency account access must not leak unrelated client campaigns.
- Public dashboards open a Calendar/Campaigns section chooser with Back navigation; followers use a range-free compact view at entry, agency keeps section tabs. Why: separate public workflows without changing agency configuration.
- Social followers discover owned/client pages and linked Instagram from the selected portfolio using server-side agency/Page tokens, with legacy connections as fallback. Why: portfolio-connected clients need no separate legacy OAuth setup.
- Structured content plans are stored as self-contained HTML in `agency_proposals.html_content` with their editable data embedded in a `socialify-content-plan` JSON script (`src/lib/content-plan.ts`). Why: public `/plan/:slug` rendering and existing HTML plans keep working without schema or RPC changes.
